# Phase 0 Decision Register

**Status:** Proposed decision package. No production implementation is authorized by this document.
**Prepared:** 2026-11-14
**Source of truth:** Approved ADRs and specifications remain controlling. Recommendations below are proposals unless marked `CONFIRMED_EXISTING_ADR`. Every policy, provider, or ownership selection requiring approval is marked `OWNER_DECISION_REQUIRED`.

## Decision status meanings

- `APPROVED`: the owner has approved this decision; the approval does not authorize implementation beyond its stated scope.
- `PENDING`: the decision remains unresolved and requires the named owner(s); any proposed option remains a proposal.
- `CONFIRMED_EXISTING_ADR`: already approved in the listed project decision; preserve it.
- `OWNER_DECISION_REQUIRED`: the approval dependency for a pending decision; do not implement until the named owner approves.
- `BLOCKED`: required evidence or policy is missing.

## Owner-approved decisions

### DECISION-001 — National Football Identity

- **Status:** `APPROVED`
- **Decision statement:** The National Football ID belongs to the player, not an organization. The same player retains the same ID across SSBs, clubs, academies, tournaments, competitions, transfers, affiliation changes, and future association/federation integrations. Organization membership, team membership, competition registration, and transfer never create a new player identity. Identity is independent of current organization and primary context.
- **Rationale:** Establishes the PRD principle “The player owns the journey” and preserves identity continuity across the ecosystem.
- **Consequences:** The player identity/Football ID is the stable subject key. Affiliation and team-membership history are separate dated relationships and may change without replacing identity. New domains reference the same player identity; journey records retain source provenance. Primary context remains presentation-only and cannot authorize access. Future data modeling must not use a current organization/team column as identity ownership.
- **Approval state:** Owner-approved for planning. Schema, provider, and implementation decisions remain separate.

### DECISION-002 — Child Data Development Restriction

- **Status:** `APPROVED`
- **Decision statement:** Initial development and testing use adult test accounts only for account/authentication tests and synthetic/dummy player data for player profiles and football records. Do not import, collect, or use real children's personal data; enable real child-profile sharing; enable real scouting discovery involving children; or expose real child data to scouts, clubs, academies, or other organizations.
- **Rationale:** Keep real child data out of development until safeguards are designed, implemented, independently reviewed, and tested.
- **Consequences:** This is a development restriction, not permission to implement a real child-data system and not a legal-compliance conclusion. Real child data remains prohibited until every release gate listed in the Child Protection Readiness section is approved and verified. Do not infer a legal age threshold.
- **Approval state:** Owner-approved. This decision does not approve provider selection, real-data import, sharing, scouting, or production child-data access.

### DECISION-003 — Existing Backend and Database Provider Inspection

- **Status:** `APPROVED`
- **Decision statement:** Before provider selection or connection, inspect the existing repository and Lovable/provider environment for an existing backend, Lovable-managed database, connected Supabase project, application integration, usability, owner access/control, authentication, database, storage, and deployment configuration, and whether the backend can meet security, privacy, tenant-isolation, and child-safety needs. Do not create, connect, disconnect, replace, configure, migrate, export production data, or push configuration as part of this inspection.
- **Rationale:** Provider choice must be evidence-based and must not create parallel infrastructure or disrupt existing ownership.
- **Consequences:** Repository evidence alone is insufficient to establish remote backend existence or control. Lovable/provider dashboard inspection must be performed by an authorized owner. Provider selection remains `PENDING` until evidence is collected and the owner explicitly approves a choice.
- **Approval state:** Owner-approved prerequisite for inspection only. No provider connection or database change is authorized.
